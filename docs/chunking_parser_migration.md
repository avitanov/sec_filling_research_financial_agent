# SEC Filing Parsing, Chunking, and Retrieval

## Purpose

This document explains how the current parsing and chunking implementation
turns a frozen SEC 10-K HTML file into searchable, auditable evidence. It also
records why the previous custom-only parser was replaced with a hybrid approach.

The simplest mental model is a filing in a binder:

- the project HTML parser keeps the pages in order and records where tables sit;
- `sec-parser` reads each page and identifies SEC headings and meaningful tables;
- the chunker makes separately searchable copies of pages and tables;
- Qdrant acts as the searchable card catalogue;
- every search result keeps a label pointing back to its source page.

The page and table copies are intentionally both retained. A page is useful for
narrative context, while a structured table is safer for matching a row label to
the correct year and value.

## Decision

Use a pinned `sec-parser` commit for SEC-specific semantic classification while
keeping a small deterministic project layer for physical pages, table grids,
stable evidence IDs, and audit metadata.

```text
                         one frozen 10-K HTML file
                                      │
                    ┌─────────────────┴─────────────────┐
                    │                                   │
          project FilingHTMLParser             sec-parser, page by page
          "where is it physically?"            "what does it mean?"
                    │                                   │
          pages, positions, cells,             Items, Notes, titles,
          printed page numbers                 meaningful SEC tables
                    │                                   │
                    └─────────────────┬─────────────────┘
                                      │
                         match within the same page
                                      │
                         auditable evidence chunks
```

The dependency is pinned in `pyproject.toml` to Git commit
`823d199e7eac62804ac9de1b744d97b72476fec5`. This is a Git commit identifier,
not a content hash generated by this project. The published `0.58.1` package did
not expose `Edgar10KParser` during the pilot, while the pinned commit did. Using
one exact commit prevents a future library update from silently changing the
experimental dataset.

## Evolution of the Chunking Strategy

The parser and chunker evolved through three development strategies. Earlier
versions are no longer maintained; version 3 is the current supported output.

```text
version 1                 version 2                 version 3
custom parser     ──►     sec-parser hybrid  ──►    simplified hybrid
```

### Version 1: custom parser

The first version used custom HTML parsing for both physical layout and semantic
context. It produced page and table evidence, but SEC headings could be missed,
text references could be mistaken for active sections, and complex tables could
lose their row and column alignment.

### Version 2: first `sec-parser` hybrid

The second version kept the custom parser for physical pages and tables while
using `sec-parser` for SEC titles and meaningful table classification. It added
same-page table matching, structured grids, semantic metadata, fallback table
retention, and cross-page handling. The result was safer, but the implementation
still contained redundant logic and metadata and was not generic enough.

### Version 3: simplified generic hybrid

The current version keeps the same division of responsibilities but simplifies
the rules and schema. It uses generic structural signals, keeps page and table
evidence auditable, omits unavailable metadata, removes duplicate fields, and
validates lineage, checksums, and embedding length before indexing.

### Comparison of the strategies

| Concern | Version 1 | Version 2 | Version 3 |
| --- | --- | --- | --- |
| Parsing | Custom only | Custom physical parser plus `sec-parser` | Simplified hybrid |
| Tables | Basic flattened extraction | Structured semantic tables | Structured tables with generic fallback and continuation |
| Metadata | Limited and less reliable | Rich but redundant | Minimal and position-aware |
| Status | Superseded | Superseded | Current |

## End-to-End Flow

```text
data/manifest.csv + data/raw/<frozen 10-K>.html
                         │
                         ▼
              1. verify source SHA-256
                         │
                         ▼
       2. recover physical pages and physical tables
                         │
                         ▼
          3. run sec-parser on each page separately
                         │
                         ▼
       4. attach semantic context to tables in order
                         │
                         ▼
          5. rebuild rectangular logical table grids
                         │
                         ▼
        6. detect tables continued onto the next page
                         │
                         ▼
              7. create three chunk types
          ┌──────────────┼──────────────────┐
          ▼              ▼                  ▼
    filing_page     filing_table     cross_page_table
          └──────────────┼──────────────────┘
                         ▼
       8. validate lineage, coverage, size, and hashes
                         │
                         ▼
         9. create dense and BM25 representations
                         │
                         ▼
             10. store and search in Qdrant
```

No live SEC request is made during these steps. Scored work uses only the frozen
files recorded in the manifest.

## Step 1: Verify the Frozen Input

The manifest records the company, filing accession, dates, source location, and
SHA-256 checksum. Before parsing, the code recalculates the local HTML checksum
and compares it with the manifest.

```text
checksum in manifest == checksum of local HTML  → continue
checksum in manifest != checksum of local HTML  → stop with an error
```

This prevents a downloaded file from being replaced or edited without the
dataset change being visible. The source checksum is also copied into every
chunk so that a later result can identify the exact source file used.

## Step 2: Recover Physical Pages and Tables

`FilingHTMLParser` reads the complete HTML file once. It performs physical work,
not SEC semantic classification.

It records:

- normalized visible text in source order;
- physical page boundaries represented by the filing's page-break `<hr>` tags;
- outer HTML tables, their rows and cells, and their positions in page words;
- printed page numbers found in bottom-of-page footer elements.

It deliberately ignores Inline XBRL headers, scripts, styles, and hidden
elements. Absolutely positioned bottom footers are kept separate from body text
so a printed page number does not pollute retrieval.

The internal depth counters mean "how deeply nested are we inside this kind of
HTML content?":

| Counter | Why it exists |
| --- | --- |
| `_skip_depth` | Keeps an entire nested hidden/script/style subtree out of filing text |
| `_footer_depth` | Keeps a nested page footer separate until its closing tag |
| `_table_depth` | Treats an outer table as one physical fragment instead of creating duplicate fragments for nested layout tables |

For additional safety, the raw HTML is also split using the same page-break
pattern. The number of raw page fragments must equal the number produced by
`FilingHTMLParser`. If the two methods disagree, parsing stops instead of
guessing page lineage.

### Physical page sequence versus printed page number

These are different:

```text
physical sequence 124  = the 124th HTML page fragment in the file
printed page 112       = the number visibly printed in that page's footer
```

Physical sequence is always used for stable lineage. Printed page number is
optional because cover pages and some filing pages do not display one.

## Step 3: Classify Each Page With `sec-parser`

`sec-parser` is invoked separately for every raw physical page:

```text
raw page 1 HTML → sec-parser → semantic elements for page 1
raw page 2 HTML → sec-parser → semantic elements for page 2
raw page 3 HTML → sec-parser → semantic elements for page 3
```

It does not parse the whole filing and then search flattened text to recover page
numbers. Therefore, every semantic element is already associated with exactly
one physical source page.

The project walks the semantic elements in source order. A small state object
remembers the most recent useful section title, Item, and Note. That state is
carried from one page to the next because a section commonly starts on one page
and continues on later pages.

```text
page 35: "Item 8. Financial Statements ..."
                  │
                  └── active Item becomes Item 8

page 36: no new Item heading
                  │
                  └── tables still inherit Item 8

page 40: "Note 3. Acquisitions"
                  │
                  └── active Note becomes Note 3
```

Only semantic title elements update that state. An ordinary sentence such as
"See Note 10" does not become the active Note merely because it contains those
words.


## Step 4: Decide Which Physical Tables Receive Table Chunks

Every visible HTML table remains part of the complete page text, but not every
HTML table deserves a separate structured-table chunk. SEC HTML also uses tables
for page layout, checkboxes, headers, and tables of contents.

There are two ways to retain a physical table.

### Normal path: `sec-parser` recognizes a table

```text
physical table found by FilingHTMLParser on page N
                         │
       sec-parser emits TableElement on page N
                         │
       normalize both table texts for comparison
                         │
       exactly one unused physical table matches
                         │
                  retain the table
             parser_source = "sec-parser"
```

Matching happens only on the same page. Row markers, cell separators, case, and
whitespace are removed for matching. A physical table can be used only once. If
zero or multiple physical tables match a `TableElement`, the build stops with a
clear error rather than attaching semantic metadata to an uncertain table.

`TableOfContentsElement` is explicitly excluded from synthetic table chunks.
Its words are still present in its ordinary page chunk.

### Numeric fallback: `sec-parser` emits ordinary text

SEC filings use inconsistent HTML, so `sec-parser` can occasionally classify a
meaningful numeric table as ordinary text. Without the fallback, its values
would remain only in flattened page text and no precise `filing_table` chunk
would preserve the row-and-column structure. The fallback retains it only when
strong structural, numeric, and unit signals are present, which limits layout
noise and false table chunks.

```text
unused physical table on the same page
                  │
its normalized text occurs inside this semantic text element
                  │
                  ├── at least 2 rows
                  ├── at least 4 cells in total
                  ├── at least 2 cells containing numbers
                  ├── first non-empty cell is not "Page"
                  └── has $ or %, OR nearby context says
                      thousands / millions / billions
                  │
                  ▼
            retain the table
   parser_source = "numeric-text-fallback"
```

There is intentionally no list of thousands of financial terms. The fallback
uses table structure, numeric content, and unit evidence instead. This keeps the
rule understandable and avoids tuning a vocabulary to the current companies.

Example retained by the fallback:

```text
                         2025       2024
Expected cash vesting    $ 418      $ 376
Expected share vesting     102         95
```

It has multiple rows and numeric cells plus a currency sign. A one-cell layout
table containing `Page 84` does not pass.

## Step 5: Rebuild the Logical Table Grid

HTML tables often use `rowspan` and `colspan`. Flattening only non-empty cells
can shift a value under the wrong year.

Suppose the source visually means:

|  | 2024 | 2025 |
| --- | ---: | ---: |
| Revenue | $100 | $120 |

A flattened sentence could become:

```text
2024 2025 Revenue $100 $120
```

The relationships are now implicit. The structured chunk instead uses explicit
markers:

```text
[TABLE]
[ROW] [BLANK] | 2024 | 2025
[ROW] Revenue | $100 | $120
```

The grid reconstruction:

1. expands `colspan` and `rowspan` into their logical positions;
2. preserves structural gaps as empty cells;
3. pads every row to the same width;
4. removes only a column that is empty in every row;
5. renders remaining gaps as `[BLANK]` and separates rows with `[ROW]`.

This representation is still plain text, so both dense search and BM25 can use
it, but the row and column relationships remain visible to later components.

## Step 6: Attach Context and Table Metadata

Metadata is attached when the table is encountered, not after scanning the
whole page. This matters when a page contains a table followed by the next
section heading.

For each retained table the code records, when available:

- the active section title, Item, and Note;
- up to 60 words immediately before the table on the same physical page;
- a nearby unit qualifier such as `in millions`;
- explicit units inferred from `$`, `%`, or a per-share qualifier;
- four-digit calendar years appearing in the table;
- row count, column count, fragment ID, source page, and parser route.

The raw qualifier is embedded directly in `core_text` as `[UNIT]`; it is not
duplicated as a standalone `FilingChunk` field. Likewise, the nearby table
context is embedded as `[CONTEXT]` and is not stored twice.

Example table `core_text`:

```text
Consolidated Results
[CONTEXT] The following table presents results in millions, except per-share data
[UNIT] in millions, except per-share data
[TABLE]
[ROW] [BLANK] | 2024 | 2025
[ROW] Revenue | $ | 100 | $ | 120
```


## Step 7: Detect Cross-Page Table Continuations

Every retained physical table always receives its own `filing_table` chunk.
Continuation detection adds a relationship; it never deletes or replaces those
individual table chunks.

Only adjacent physical pages are considered. Candidate tables must be near the
page boundary: within 40 words of the end of the left page and within 40 words
of the beginning of the right page.

```text
page N                                     page N+1

... narrative ...                         table continuation ...
┌───────────────────────┐                 ┌───────────────────────┐
│ table near page end   │ ──────────────► │ table near page start │
└───────────────────────┘                 └───────────────────────┘
```

The boundary pair is connected when at least one generic signal exists:

1. **Matching row labels:** after numbers and punctuation are removed, the two
   tables share at least two row labels and their set similarity is at least
   `0.60`.
2. **Repeated descriptive first row:** the normalized first rows are identical,
   unless that row is only a generic period heading such as `Year Ended 2025`.
3. **Physical split:** the left table reaches the end of its page and the right
   table starts within the first six page words.

### Cross-page continuation examples

All examples below assume the left table is near the end of page N and the right
table is near the beginning of page N+1. Without that physical proximity, the
tables are not considered a continuation pair.

#### 1. Repeated descriptive column header: connect

```text
page N, table near end                 page N+1, table near start

[ROW] Geographic area | Revenue        [ROW] Geographic area | Revenue
[ROW] Europe          | 120             [ROW] Asia            | 90
[ROW] Americas        | 180             [ROW] Other           | 15
```

The first row is the same descriptive column header on both pages. This is
evidence that the second table continues the same layout, even though the data
rows are different.

#### 2. Strongly overlapping row labels: connect

```text
page N                                  page N+1

[ROW] Revenue           | 400            [ROW] Revenue           | 400
[ROW] Operating income  | 80             [ROW] Operating income  | 80
[ROW] Net income        | 60             [ROW] Net income        | 60
[ROW] Income tax        | 20             [ROW] Earnings per share| 1.25
```

The tables share three descriptive row labels. Their Jaccard similarity is
`3 / 5 = 0.60`, so they meet the row-label continuation rule. This is useful for
repeated panels of the same table or a table whose headers are not repeated.

#### 3. Direct HTML split at the page break: connect

```text
page N ends immediately after table       page N+1 starts with table

[ROW] Revenue | 400                       [ROW] Cost | 250
                                         [ROW] Gross profit | 150
```

Here the parser records that the left table reaches the actual end of the page
and the right table begins within the first six words of the next page. That
physical split is enough to connect them, even if no header or row labels repeat.

#### Matching years alone: do not connect

```text
page N table                              page N+1 unrelated table

[ROW] [BLANK] | 2025 | 2024               [ROW] [BLANK] | 2025 | 2024
[ROW] Revenue | 400  | 360                 [ROW] Lease expense | 12 | 10
```

The years match, but year columns such as `2025 | 2024` appear in many unrelated
financial tables. Generic period headers are therefore deliberately excluded as
continuation evidence. A separate descriptive-header, row-label, or physical-
split signal is required.

### Jaccard similarity for row labels

The first continuation signal uses **Jaccard similarity**, a standard way to
compare two sets. It asks: "Of all distinct labels seen across both tables, what
fraction appears in both?"

```text
Jaccard(A, B) = size of (A intersect B) / size of (A union B)
```

The result ranges from `0` to `1`:

- `0` means the tables share no row labels;
- `1` means they have the same set of row labels;
- values between them represent partial overlap.

Before comparing tables, the code examines each row from left to right and keeps
the first descriptive cell that remains meaningful after removing numbers,
currency symbols, percentage symbols, brackets, commas, decimal punctuation,
dashes, and underscores. The labels are stored in sets, so a repeated label does
not artificially increase the score.

Example:

```text
left labels  = {revenue, operating income, net income, income tax}
right labels = {revenue, operating income, net income}

shared labels = {revenue, operating income, net income}  → 3
all labels    = {revenue, operating income, net income, income tax} → 4

Jaccard similarity = 3 / 4 = 0.75
```

This passes the current `0.60` threshold and also satisfies the separate safety
rule requiring at least two shared labels. The second rule matters because two
very small tables could otherwise obtain a high similarity from only one vague
label.

Jaccard similarity alone does not prove continuation. That is why it is applied
only to tables near adjacent page edges.

The rules contain no company-specific statement-name list and no special keywords. Additional consecutive panels on either
boundary page are included only when they match the same generic row-label or
descriptive-header evidence.

Connected fragments receive one deterministic `continuation_group_id`:

```text
page 70 / table 2 ─┐
page 71 / table 1 ─┼── continuation_group_id = ...table-group-004
page 72 / table 1 ─┘
```

Missing title, context, qualifier, and units can be inherited from another
fragment in the same group. Each fragment still retains its own page lineage.

### Why the combined chunk has a 900-word limit

If the raw table fragments together contain at most 900 words, the chunker also
creates one `cross_page_table` chunk with `[PAGE BREAK]` between fragments.

```text
[TABLE] fragment from page 70
[PAGE BREAK]
[TABLE] fragment from page 71
```

The 900-word rule is a conservative pre-embedding guard. It avoids producing a
very large duplicate chunk merely because several tables belong to the same
group. Exact model tokens are checked later against the 2,048-token model limit.

If a group exceeds 900 words:

- no combined `cross_page_table` chunk is created;
- all individual `filing_table` chunks remain searchable;
- all fragments retain the same `continuation_group_id`.

Therefore, the limit can remove a convenience copy, but it cannot remove the
underlying table evidence.

## Step 8: Create the Three Evidence Types

### `filing_page`

One chunk is created for every physical page.

```text
previous page: last 100 words ─┐
                               ├── indexed_text used for retrieval
current page: complete text ───┤
                               │
next page: first 100 words ────┘

current page only ──────────────── core_text returned as evidence
```

The overlap helps a search find a concept split at a page boundary. It does not
change which page owns the evidence. The previous and next overlap text, word
counts, and page IDs are stored separately.

### `filing_table`

One additional chunk is created for every retained meaningful table. It contains
the title, nearby context, unit qualifier, and structured grid. It has no page
overlap because it already represents a precise physical table.

### `cross_page_table`

One additional combined chunk is created for a continuation group only when the
group is within the 900-word limit. Its `supporting_page_ids`,
`supporting_page_sequences`, and `table_fragment_ids` list every source used.

### Stable IDs

Human-readable evidence IDs are deterministic:

```text
filing-ko-2025-page-0012
filing-ko-2025-page-0012-table-01
filing-ko-2025-table-group-003
```

Qdrant also requires a point ID. The code derives a UUIDv5 from the evidence ID
and one fixed `POINT_NAMESPACE`. The same evidence ID therefore produces the
same point ID after every rebuild. The namespace does not alter chunk content or
search ranking.

## Metadata and Empty Values

Every payload carries the provenance required to audit it:

- evidence type and stable evidence ID;
- company, ticker, CIK, accession, document type, and filing dates;
- source path, source URL, source checksum, parser version, and schema version;
- supporting physical page IDs and sequences;
- content checksum and word counts;
- relevant page, Item, Note, overlap, continuation, or table metadata.

Some metadata is naturally unavailable. A cover page may have no printed page
number, and a table may have no unit. `compact_metadata()` removes `None`, empty
strings, empty lists, and empty dictionaries before the chunk becomes a Qdrant
payload.

```text
available value   → store the field and its value
unavailable value → omit the optional field entirely
```

This prevents misleading empty metadata without inventing values that do not
exist in the source. Required lineage fields such as supporting page lists are
validated rather than omitted.

## Validation Before Indexing

Chunk construction stops if a deterministic invariant fails. The checks cover:

- exactly one page chunk per parsed physical page;
- exactly one individual table chunk per retained meaningful table;
- unique evidence IDs;
- correct page ownership and exact overlap sizes;
- non-empty page `core_text`;
- rectangular table grids;
- matching Item, Note, and period metadata;
- continuation groups spanning at least two valid pages;
- valid supporting page and table-fragment IDs;
- matching source and chunk-content SHA-256 checksums.

Embedding adds another check. Token counting is performed with truncation turned
off. A filing chunk above 2,048 model tokens fails the build instead of being
silently shortened.

Search queries are different because they come from users at runtime. A query
above the limit may be truncated by the tokenizer, and the returned metadata
includes a `query_truncation_message` so this is observable.

## Embedding and Retrieval

Each chunk is stored in two searchable forms:

```text
indexed_text
    ├── dense embedding: meaning and semantic similarity
    └── BM25 document: exact words, names, labels, and numbers
```

The two routes solve complementary problems. Dense retrieval can connect a
question with a semantically related passage even when the wording differs.
BM25 is strong when exact words, company terminology, row labels, years, or
numbers matter.

### Dense embeddings and the Snowflake model

The dense model is
[`snowflake/snowflake-arctic-embed-m-long`](https://huggingface.co/Snowflake/snowflake-arctic-embed-m-long).
Its official model card describes the long-context model, recommends CLS-token
pooling, and specifies the query-only retrieval prefix used here.

The project configures a 2,048-token input limit and 768-dimensional vectors.
The model is loaded through `load_embedding_model()`, which is cached with
`lru_cache(maxsize=1)`. This means it is loaded once and reused within a Python
process rather than being loaded again by every embedding function.

An embedding is a fixed-length numeric representation of text:

```text
"operating income increased" ──► [0.018, -0.042, 0.007, ...]
```

Texts with related meanings should point in similar directions in this vector
space. Qdrant compares the dense vectors using cosine similarity.

### Why the query prefix is required

Documents are embedded as written. Queries receive the model's retrieval prefix:

```text
Represent this sentence for searching relevant passages: <user query>
```

This is an **asymmetric retrieval** setup: a short question and a source passage
play different roles. The prefix tells the model that this input is the search
request whose matching passages should be found.

```text
filing chunk:  "Net sales increased ..."              → document vector
query:         "What were net sales in 2025?"         → not embedded directly
prefixed query:"Represent this sentence ...: What ..." → query vector
```

The prefix is added only by `embed_query()`. It is not stored with the question,
not added to filing chunks, and not shown in the returned evidence. Token
counting includes the prefix so the query's true model input length is measured.

Using the same model without its recommended prefix would still produce a
vector, but it would not follow the retrieval procedure documented by the model
authors and may reduce matching quality.

### CLS pooling and normalization

The tokenizer places a special classification token, `[CLS]`, at the beginning
of the token sequence. When FastEmbed receives token-level model output, its
installed ONNX implementation selects the vector at position zero—the CLS
vector—as the single representation for the whole input. It then normalizes the
vector to unit length.

```text
[CLS] token₁ token₂ ... tokenₙ [SEP]
  │
  └── first-token vector ──► L2 normalization ──► stored dense vector
```

Normalization makes direction, rather than raw vector magnitude, the important
part of cosine comparison. This matches the Snowflake model card's CLS-pooling
recommendation. The project does not implement a second manual pooling step;
doing so would transform an already prepared embedding incorrectly.

### Token counting and truncation

The runtime tokenizer is configured for the project's 2,048-token limit, but
filing chunks are checked before embedding with truncation disabled. If a chunk
is too long, indexing fails with its evidence ID and token count. This prevents
the end of a filing page or table from disappearing silently.

Queries arrive at runtime and are treated differently. An oversized query can
be truncated by the tokenizer, but the search result metadata receives a
`query_truncation_message`. The event is therefore visible to evaluation and
debugging code.

### BM25 sparse retrieval

The sparse route uses [`qdrant/bm25`](https://huggingface.co/Qdrant/bm25).
[Qdrant's BM25 documentation](https://qdrant.tech/documentation/search/text-search/full-text-search/)
explains the three central signals:

- term frequency: a matching term appearing more often can be more relevant;
- inverse document frequency (IDF): a rare term is more informative than a very
  common term;
- document length: the same match can carry more weight in a shorter document.

Sparse means that only dimensions corresponding to terms present in the text
need non-zero values. The collection enables Qdrant's `IDF` modifier, allowing
Qdrant to use corpus-level term rarity when scoring BM25 matches.

For example, dense retrieval may understand that "sales" and "revenue" are
related, while BM25 can strongly reward an exact label such as `AWS`, a specific
year, or an unusual accounting phrase.

### Reciprocal-rank fusion

Dense cosine scores and BM25 scores do not live on the same numerical scale, so
the code does not add their raw scores together. It uses Qdrant's
[hybrid-query prefetch and reciprocal-rank fusion](https://qdrant.tech/documentation/search/hybrid-queries/)
instead.

Reciprocal-rank fusion (RRF) uses each result's position in a ranked list. A
chunk receives more credit when it ranks near the top, and it receives credit
from both routes when both retrieve it.

```text
dense ranking:  table A, page B, table C
BM25 ranking:   table C, table A, page D
                          │
                          ▼
RRF ranking: results favored by strong positions across the two lists
```

Rank-based fusion avoids pretending that a dense score and a BM25 score are
directly comparable. The implementation then applies one deterministic
relationship already present in the chunk metadata: a table can inherit the
RRF score of its supporting page.

```text
table ranking score = table RRF score + supporting page RRF score
```

This solves a specific duplication problem. A complete page often ranks well
because it contains broad context, while its shorter structured table ranks
lower even though it contains the precise rows and values. The linked score
moves that table upward without checking for company-specific terms or calling
a neural reranker. Both original components are returned as `fusion_score` and
`linked_page_score` for auditing.

### Retrieval strategy: relationship-aware hybrid ranking

The previous retrieval strategy was plain hybrid ranking: dense search and BM25
were fused with RRF, then the first five chunks were returned. The current
strategy keeps that foundation and adds an existing structural relationship:
when a relevant page supports a table, the table can use that page's relevance
when it is ranked.

The change happened in three small steps. It changes query-time ranking only:
it does not change the parsed source, chunk text, evidence IDs, or the Qdrant
index.

#### 1. Original hybrid ranking

Dense and BM25 search each supplied a small candidate list. RRF ranked the
combined candidates and returned the first five. A broad page could rank high
while its exact table remained below the cutoff.

```text
Question: "What was the segment operating income in 2025?"

RRF ranking before table adjustment
1. Page 27                 broad explanation and the table text
2. Page 18                 another related page
3. Table from Page 68      different table
4. Page 25                 related discussion
5. Page 67                 related discussion
6. Page 27, Table 01       exact segment values  ← not returned
```

The table was not missing. It simply did not rank high enough to be included in
the five returned results.

#### 2. Larger candidate pool

The candidate pool was increased before fusion. This gives RRF more page and
table choices to compare before the final top-five cutoff.

```text
before: dense candidates + BM25 candidates → small pool → top 5
after:  dense candidates + BM25 candidates → larger pool → top 5
```

This can bring a previously overlooked table into the pool, but it does not by
itself guarantee that the table outranks broad page chunks.

#### 3. Supporting-page score for tables

Every table chunk already records which physical page or pages support it. If a
supporting page is strongly relevant, its score is added to that table's own
RRF score. Page scores are never increased by table scores.

```text
Page 27
└── Table 01

Page 27 RRF score:       0.54
Table 01 RRF score:      0.22
                           +
Table 01 final score:    0.76
```

The system then sorts the same candidate chunks again and returns exactly five
results. It does not append a sixth table result.

```text
Ranking after table adjustment
1. Page 27, Table 01       0.76  ← exact values now returned
2. Page 27                 0.54  ← surrounding explanation
3. Page 18                 0.40
4. Table from Page 68      0.35
5. Page 25                 0.30
6. Page 67                 0.28  ← displaced, not returned
```

For a cross-page table, the table uses the strongest score among its supporting
pages. This lets a combined table receive useful context from either side of
the page break.

```text
cross-page table score = table RRF score + max(Page N score, Page N+1 score)
```

### Company filtering and candidate selection

For each search, Qdrant:

1. rejects a ticker not present in the frozen manifest;
2. filters both dense and BM25 candidate searches to that company;
3. retrieves the configured candidate pool from each route, 30 by default, or
   twice the requested final limit when that is larger;
4. combines the two rankings with reciprocal-rank fusion;
5. adds supporting-page relevance to linked table candidates;
6. returns the requested number of results, five by default.

```text
user query
   ├── dense candidates ─┐
   └── BM25 candidates ──┼── RRF ──► linked table adjustment ──► top results
                         │
                company filter on both routes
```

The ticker filter is applied inside both prefetch searches, not after fusion.
Evidence from another company therefore cannot occupy a candidate position and
then be removed too late. A keyword payload index on `ticker` makes this filter
efficient. An `evidence_type` keyword index is also created for exact chunk-type
filtering, although the current `search_filing()` function does not restrict
results by evidence type.

The caller receives the human-readable evidence ID, final ranking score,
returned `text`, and payload metadata. The payload preserves `fusion_score`
and `linked_page_score`, so the table adjustment remains inspectable. For page
chunks, the returned `text` is `indexed_text`: the page's `core_text` together
with its neighbouring overlap. The clean current-page `core_text` remains in
the payload for audit and page-specific citations.

The Qdrant collection is recreated during `rebuild`. Payload validation then
builds the chunks again in memory and compares their evidence IDs and payloads
with the stored points. It does not call the SEC or silently repair mismatches.

### Similar-looking identifiers and hashes

The implementation uses three mechanisms that serve different purposes:

| Value | Purpose | Affects ranking? |
| --- | --- | --- |
| `source_sha256` | Proves the frozen HTML still matches the manifest | No |
| `content_sha256` | Proves the exact indexed chunk text has not changed | No |
| UUIDv5 Qdrant point ID | Converts a stable evidence ID into a deterministic database ID | No |

These values support reproducibility and auditability. They are identifiers and
integrity checks, not embedding features.

### Table structure was flattened

The old representation preserved words and numbers but not reliable row and
column relationships. It ignored span structure and appended only non-empty
cells, allowing values to shift left.

Old flattened example:

```text
2023 2024 2025 Net product sales $255,887 $272,311 $296,266
Net service sales 318,898 365,648 420,658
```

Current structured example:

```text
[ROW] [BLANK] | 2023 | [BLANK] | 2024 | [BLANK] | 2025 | [BLANK]
[ROW] Net product sales | $ | 255,887 | $ | 272,311 | $ | 296,266
[ROW] Net service sales | [BLANK] | 318,898 | [BLANK] | 365,648 | [BLANK] | 420,658
```

### Every HTML table was treated as financial evidence

SEC HTML uses tables for layout as well as data. The old parser collected
checkbox, header, and table-of-contents structures as if they were financial
tables. `sec-parser` makes the main semantic decision, while the narrow numeric
fallback covers meaningful tables that it emits as text.

### Cross-page rules were case-specific

The old continuation approach relied on a short manually configured list. The
current implementation uses page position, row-label similarity, repeated
descriptive headers, and direct physical splits. It does not contain hardcoded
company names, financial-statement names, exhibit/signature checks, or a large
financial-term vocabulary.

## Why `sec-parser` Was Chosen

It was the smallest tested library designed specifically for SEC EDGAR HTML. It
provided useful SEC title and table classification while still allowing the
project to preserve physical pages and verify every semantic-to-physical table
mapping explicitly.

The alternatives did not fit this narrow requirement as well:

- LangGraph orchestrates workflows; it is not a document parser.
- LlamaIndex's generic HTML parsing relies more heavily on conventional
  paragraph and heading tags, which do not match styled SEC markup reliably.
- LangChain generally wraps another loader and would add an abstraction layer
  without solving physical page and SEC semantic classification.
- Unstructured extracted useful tables in the pilot but did not preserve the
  required physical pages or useful AMZN semantic titles.
- Docling recognized tables but did not preserve the HTML pages, expanded SEC
  layouts noisily, and added a larger dependency surface.
- Arelle is appropriate for Inline XBRL fact validation, not narrative and
  page-aware retrieval chunks.

`sec-parser` is not used as the only parser because its semantic elements do not
provide the physical page, page-relative table positions, stable project IDs,
or exact chunk schema required by this experiment. The hybrid keeps each tool
focused on the information it can reliably provide.
